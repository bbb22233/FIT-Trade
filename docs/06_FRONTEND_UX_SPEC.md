## 3. UX 目标与原则

### 3.1 主要目标

1. 用户可以同时看到市场、账户、持仓、风险和 Hermes 上下文。
2. 自然语言建议必须转化为结构化、可核对的交易意图。
3. 模型建议、用户确认和服务端执行事实必须在视觉上严格分离。
4. 增加风险不能因误触、过期数据、重复点击或模型文本而绕过确认。
5. 异常状态必须优先于普通行情和盈亏信息显示。
6. 学习、候选版本和自动交易授权必须可追溯、可纠正、可撤销。

### 3.2 交互原则

- 安全优先于操作速度。
- 风险优先于潜在收益。
- 服务端事实优先于客户端推测和模型表述。
- 当前状态优先于历史状态。
- 主网、模拟和假设讨论始终明确区分。
- 危险状态不依赖颜色单独表达。
- 不使用刺激频繁交易的游戏化、庆祝动画或收益诱导。
- 任何不可逆动作都应显示其实际对象、范围和当前权威状态。

### 3.3 三类信息的视觉边界

| 信息类型 | 权威来源 | 表现要求 |
| --- | --- | --- |
| Hermes 分析与建议 | 模型输出 | 标记为“分析”或“建议”，不得伪装成系统状态。 |
| 用户意图与确认 | 用户操作 + 服务端确认对象 | 使用独立结构化组件，绑定确认哈希、nonce 和有效期。 |
| 订单、成交、仓位和保护状态 | Go 核心和 Hyperliquid 核对结果 | 使用系统状态组件，不从聊天文本推导。 |

## 4. 信息架构

### 4.1 全局结构

桌面软件使用“固定状态栏 + 左侧导航 + 中央交易工作区 + 右侧 Hermes + 底部交易面板”的结构。

全局区域：

- 顶部状态栏
  - `MAINNET` 环境
  - 当前账户
  - 市场数据状态
  - 账户数据状态
  - 持仓保护总状态
  - 自动交易状态
  - 通知入口
  - Kill Switch
- 左侧主导航
- 中央页面内容
- 右侧 Hermes 常驻面板
- 全局最高级别告警层

### 4.2 主导航

1. 指挥中心
2. 持仓与订单
3. 风险与安全
4. 复盘与学习
5. 自动交易
6. 活动与审计
7. 设置

Hermes 不作为只能单独进入的导航页面。它在指挥中心常驻，在其他页面可收起或重新展开，并带入当前对象上下文。

## 5. 页面交付优先级

### 5.1 P0：指挥交易与安全基础

| 页面或模块 | 目标 | 必须覆盖的状态 |
| --- | --- | --- |
| 登录与设备登记 | 建立用户、设备和会话上下文 | 登录失败、限速、会话过期、设备撤销 |
| 首次配置向导 | 完成钱包、账户、风险、模型和健康检查 | 未配置、部分完成、检查失败、只读完成 |
| 指挥中心 | 集中展示图表、账户、持仓、订单和 Hermes | `LIVE`、`STALE`、`RECONCILING` |
| Hermes 聊天 | 市场讨论、账户查询和自然语言交易指令 | 分析、模拟、实盘意图、模型失败 |
| 交易确认卡 | 确认所有增加风险的动作 | 待确认、已确认、已过期、已失效 |
| 执行进度 | 展示服务端 Operation 和订单状态 | 复核、派发、已确认、未知、拒绝、完成 |
| 持仓详情 | 管理持仓、止损和止盈 | 部分成交、已保护、保护调整、保护失败 |
| 持仓与订单 | 查看权威订单和成交投影 | 活动、部分成交、已取消、未知、核对中 |
| 风险与安全 | 配置和查看确定性风险边界 | 正常、接近限制、已达限制、暂停 |
| Kill Switch | 立即阻止增加风险 | 可触发、已触发、系统暂停 |
| 全局告警 | 展示保护失败、紧急退出和未知订单 | 未读、已读、待处理、已解决 |
| 基础设置 | 管理账户、设备、钱包、模型和通知 | 正常、未配置、验证失败、已撤销 |

### 5.2 P1：学习与受限自动交易

| 页面或模块 | 目标 | 必须覆盖的状态 |
| --- | --- | --- |
| 交易复盘 | 对比计划、执行、费用和结果 | 待生成、待反馈、已确认、已修订 |
| 学习数据管理 | 查看、纠正、撤回和删除样本 | 不可学习、可学习、已加入、已撤回 |
| 风格模型版本 | 查看当前版本和候选版本 | 草稿、验证中、影子运行、可批准、已归档 |
| 候选对比 | 比较模型、数据集、风险和指标 | 数据不足、未通过、通过待批准 |
| 自动交易授权 | 固定账户、品种、杠杆、资金和动作范围 | 草稿、待设备认证、已启用 |
| 自动交易监控 | 展示运行、暂停和决策状态 | `DISABLED`、`ENABLED`、`SAFETY_PAUSED` |
| 自动决策日志 | 追踪 Proposal、Review、Go 风控和 `NO_TRADE` | 通过、拒绝、超时、无效输出 |
| 审计与通知中心 | 查询完整事件和投递结果 | 已送达、失败、重试、已确认 |

## 6. 桌面布局规范

### 6.1 基准画布

- 主要设计基准：1440 × 900。
- 最小支持桌面宽度：1100。
- 主要布局适配：1280、1440、1728 和更宽屏幕。
- 所有宽度下必须保留主网环境、数据状态、保护状态和 Kill Switch。

### 6.2 指挥中心布局

| 区域 | 建议尺寸 | 行为 |
| --- | --- | --- |
| 顶部状态栏 | 40–48 px 高 | 固定，不随内容滚动消失。 |
| 左侧导航 | 56–64 px 收起；200–224 px 展开 | 默认收起，以图标和提示显示。 |
| 中央图表区 | 弹性宽度，建议不小于 680 px | 作为第一视觉中心。 |
| Hermes 面板 | 380–440 px | 1440 及以上常驻；允许用户调整宽度。 |
| 底部交易面板 | 220–320 px 高 | 在持仓、订单、成交和日志标签间切换。 |

中央图表区顶部包含：

- BTC、ETH、SOL 品种切换
- 1m、1h、4h 周期切换
- 标记价格、预言机价格、资金费率和未平仓量
- 图表工具、指标和 Hermes 叠加开关
- 当前数据时间和数据状态

### 6.3 宽度降级

- 1280–1439：
  - Hermes 缩小到 340–380 px。
  - 左侧导航保持收起。
  - 市场摘要合并为紧凑工具栏。
- 1100–1279：
  - Hermes 默认变为右侧可展开面板。
  - 展开 Hermes 时图表仍不小于安全可读宽度。
  - 底部持仓面板保持可访问。
- 小于 1100：
  - 网页显示“不适合完整交易工作区”的提示。
  - 允许进入监控、聊天、确认和紧急操作的窄屏模式。
  - 不把复杂图表压缩成不可读布局。

### 6.4 信息密度

- 行情、仓位和订单使用表格作为主要呈现方式。
- 表格支持列宽调整、排序、固定关键列和密度设置。
- 默认行高建议 32–36 px。
- 数字右对齐，文字左对齐，状态居中或左对齐。
- 价格、数量、金额和百分比使用等宽数字。
- 盈亏数字不应导致布局随刷新跳动。

## 7. 关键用户流程

### 7.1 首次配置

```text
账户登录
→ 登记当前设备
→ 阅读主网和独立钱包边界
→ 配置独立 Hyperliquid 交易账户
→ 配置专用 API Wallet
→ 只读获取账户、仓位、订单和成交
→ 设置用户风险参数
→ 配置 Hermes 模型 API
→ 运行连接、权限、数据和通知检查
→ 进入只读指挥中心
```

规则：

- 不显示主钱包私钥或助记词输入框。
- 不允许通过普通文本框收集设备密码。
- 单项配置失败时保留已完成的非敏感进度。
- 完成配置不等于启用实盘。
- 未取得单独实盘授权时，交易入口必须显示为只读或模拟。

### 7.2 聊天指挥开仓

```text
用户输入自然语言
→ 系统识别为讨论、假设、模拟或实盘意图
→ Hermes 获取市场、账户和风险上下文
→ 补问缺失的杠杆、止损或订单类型
→ 可选询问交易理由
→ Hermes 创建结构化交易意图
→ Go 风控计算并检查
→ 服务端创建不可修改确认快照
→ 客户端渲染结构化确认卡
```

规则：

- 未指定杠杆时不得进入可确认状态。
- 没有有效 Stop Market 时不得进入可确认状态。
- 非 BTC、ETH、SOL 不得进入实盘确认状态。
- Hermes 自由文本只能解释建议，不能构造“已确认”或“已下单”状态。

### 7.3 确认与执行

```text
用户核对确认卡
→ 点击“确认实盘开仓”或“确认加仓”
→ 按钮锁定并等待服务端接收
→ 服务端重新验证账户、市场和风险
→ 派发执行
→ 核对订单和成交
→ 创建并核对 Stop Market
→ 返回最终持仓和保护状态
```

客户端需要逐步显示：

1. 已提交确认
2. 风险重新验证
3. 正在派发
4. 等待交易所结果
5. 正在核对订单与成交
6. 正在建立或调整保护
7. 持仓已保护，或进入异常处理

客户端不得在 `ACKNOWLEDGED` 前显示“交易成功”，也不得在止损尚未核对时显示“持仓已保护”。

### 7.4 持仓管理

- 平仓、`reduce-only` 减仓、收紧止损和撤销未成交开仓订单是降低风险动作。
- 用户明确发出降低风险指令后可直接进入服务端执行，不生成增加风险确认卡。
- 加仓、提高杠杆、反向开仓、增加订单数量和放宽止损必须重新生成确认卡。
- 止损调整失败时继续显示旧止损，不提前显示新止损已生效。
- 部分止盈或减仓后，持续显示剩余持仓与 Stop Market 覆盖数量的核对状态。

### 7.5 复盘与学习

```text
仓位完全结束
→ Hermes 生成自动复盘
→ 展示计划、执行、成本、结果和规则一致性
→ 用户修改结构化标签
→ 用户给出明确反馈
→ 用户决定是否加入学习数据
→ 保存可追溯 Trade Episode
```

规则：

- 单笔盈利不自动标记为“正确”。
- 单笔亏损不自动标记为“错误”。
- 用户原始理由与 Hermes 标签分开显示。
- 普通聊天默认不加入学习集。
- 撤回或删除后明确显示其不再进入后续候选训练集。

### 7.6 自动交易授权

```text
选择候选版本
→ 查看样本、验证、影子运行和风险指标
→ 对比当前版本
→ 选择账户、币种、每币种杠杆、资金和风险范围
→ 选择允许的仓位管理动作
→ 展示完整授权摘要和授权哈希
→ 操作系统设备认证
→ 服务端确认授权
→ 状态变为 ENABLED
```

启用后，顶部状态栏持续显示：

- 自动交易 `ENABLED`
- 当前策略和模型版本
- 允许的 BTC、ETH、SOL 子集
- 资金或风险范围摘要
- 最近一次正式决策时间

扩大币种、杠杆、资金、风险或动作范围必须生成新授权并重新设备认证。

### 7.7 Kill Switch 与安全暂停

Kill Switch 流程：

```text
用户点击顶部 Kill Switch
→ 展示“停止开仓和增加风险”的明确作用范围
→ 用户执行
→ 服务端阻止新的风险增加
→ 已有仓位保护、止盈、减仓和平仓能力继续运行
```

Kill Switch 不提供“全部平仓”能力，也不得使用会让用户误以为仓位已被平掉的文案。

安全暂停流程：

```text
系统检测风险或系统异常
→ 状态变为 SAFETY_PAUSED
→ 全局持续告警
→ 禁止新开仓和加仓
→ 展示暂停原因和恢复检查
→ 条件恢复后仍保持暂停
→ 用户阅读恢复报告
→ 操作系统设备认证
→ 服务端恢复为 ENABLED
```

## 8. 交易确认卡规范

### 8.1 组件边界

确认卡是前端独立、安全关键的结构化组件：

- 只接受服务端确认对象。
- 不接受 Hermes Markdown 或自由文本生成字段。
- 字段不可原地编辑。
- 修改任何交易参数必须返回聊天或结构化交易表单重新生成。
- 必须绑定 `confirmation_hash`、一次性 nonce、风险版本和有效期。

### 8.2 字段顺序

确认卡按照以下顺序展示：

1. 环境和账户
   - `MAINNET`
   - Hyperliquid
   - 交易账户
2. 交易动作
   - BTC、ETH 或 SOL
   - 买入或卖出
   - 开仓、加仓或反向开仓
3. 订单
   - 市价、GTC 或 Post Only/ALO
   - 全仓或逐仓
   - 杠杆
   - 数量
   - 名义价值
   - 预计保证金
4. 价格
   - 预计入场价或限价
   - 最差允许成交价
   - 市场快照时间
5. 保护
   - Stop Market 触发价
   - 标记价格触发说明
   - 可选止盈
   - 预计强平价
6. 风险
   - 本单预计最大亏损
   - 交易前账户总风险
   - 交易后账户总风险
   - 预计手续费
   - 预计资金费
   - 预计滑点
   - 风控结果
7. 解释
   - Hermes 对用户指令的解释
   - 用户交易理由或“已跳过”
8. 确认元数据
   - 有效期倒计时
   - 风险配置版本
   - 确认单短哈希

### 8.3 视觉层级

- 第一层：`MAINNET`、动作、方向、品种。
- 第二层：最大亏损、交易后总风险、止损、强平价。
- 第三层：数量、杠杆、价格和费用。
- 第四层：解释、版本和短哈希。

潜在盈利不得成为确认卡的主要视觉焦点。

### 8.4 操作

- 主按钮文案必须具体，例如“确认实盘开多 BTC”。
- 次按钮为“取消”或“返回修改”。
- 点击确认后立即禁止重复点击。
- 客户端收到服务端拒绝或失效结果时，不允许恢复旧确认按钮。
- 过期、风险版本变化、市场快照过期或账户变化后，显示“重新生成确认卡”。

## 9. 服务端权威状态

### 9.1 基本规则

- 客户端不自行计算最终风险、强平价、确认有效性或订单最终结果。
- 客户端只根据服务端状态渲染，不通过超时推断失败。
- WebSocket 断开时保留最后数据，但明确标记为非实时。
- 重连后必须等待服务端核对完成才能恢复 `LIVE`。
- 所有状态显示更新时间、来源和可选的 Operation ID。

### 9.2 数据状态

| 状态 | 含义 | UI 行为 |
| --- | --- | --- |
| `LIVE` | 数据新鲜且核对通过 | 允许按风险规则操作。 |
| `STALE` | 数据超过新鲜度或连接异常 | 禁止增加风险；显示最后更新时间。 |
| `RECONCILING` | 正在重取快照并核对 | 禁止增加风险；展示核对进度。 |

### 9.3 Operation 状态

| 状态 | 用户文案 | 交互要求 |
| --- | --- | --- |
| `DRAFT` | 正在准备交易意图 | 不可确认。 |
| `AWAITING_CONFIRMATION` | 等待确认 | 显示有效确认卡。 |
| `EXPIRED` | 确认已过期 | 禁止确认，只能重新生成。 |
| `CONFIRMED` | 已收到确认 | 锁定确认按钮。 |
| `RISK_REVALIDATING` | 正在重新验证风险 | 禁止重复操作。 |
| `REJECTED` | 交易被拒绝 | 显示服务端理由和下一步。 |
| `ADMITTED` | 风控已放行 | 继续显示处理中，不称为已成交。 |
| `DISPATCH_PENDING` | 等待派发 | 禁止重复操作。 |
| `DISPATCHED` | 已发送至执行链路 | 等待权威结果。 |
| `ACKNOWLEDGED` | 交易所已确认请求 | 继续等待成交和保护结果。 |
| `UNKNOWN_REQUIRES_RECONCILIATION` | 订单结果未知，正在核对 | 最高级别持续告警；禁止盲目重试。 |
| `MANUAL_RECONCILIATION` | 需要人工核对 | 显示 Operation、订单 ID 和处理指引。 |
| `FINAL` | 本次 Operation 已结束 | 显示最终订单、成交、仓位和保护结果。 |

### 9.4 持仓保护状态

| 状态 | UI 表现 |
| --- | --- |
| `NO_POSITION` | 无持仓，不显示保护成功。 |
| `ENTRY_PENDING` | 入场等待中。 |
| `PARTIALLY_FILLED` | 已部分成交；突出已成交数量。 |
| `FILLED` | 已成交，正在进入保护流程。 |
| `PROTECTION_PENDING` | 持续警示“止损尚未核对完成”。 |
| `PROTECTED` | 明确显示 Stop Market 价格和覆盖数量。 |
| `ADJUSTING_PROTECTION` | 保留并显示当前有效旧保护，直到新保护核对成功。 |
| `PROTECTION_FAILED` | 最高级别持续告警。 |
| `EMERGENCY_CLOSING` | 显示系统正在降低风险，不要求再次确认。 |
| `MANUAL_RECONCILIATION` | 显示剩余风险和人工核对要求。 |
| `CLOSED` | 显示仓位已核对归零。 |

### 9.5 自动交易状态

| 状态 | UI 行为 |
| --- | --- |
| `DISABLED` | 不允许自动增加风险。 |
| `ENABLED` | 持续显示授权范围和版本。 |
| `SAFETY_PAUSED` | 禁止新开仓和加仓；允许保护和退出；不得自动恢复。 |

## 10. 异常、过期与核对体验

### 10.1 异常优先级

| 级别 | 示例 | 表现 |
| --- | --- | --- |
| Critical | 保护失败、紧急退出、订单结果未知、剩余风险无法核对 | 固定顶部告警 + 页面内详情 + 通知；不可静默关闭。 |
| High | 数据长时间不一致、签名服务异常、自动交易安全暂停 | 固定状态栏提示 + 通知中心。 |
| Medium | 模型失败、通知投递失败、单个数据源短暂过期 | 页面内提示，可查看详情。 |
| Info | 订单完成、止损调整成功、复盘生成 | 普通通知。 |

### 10.2 过期确认

- 倒计时小于安全阈值时改为警示样式。
- 到期后按钮立即禁用。
- 显示导致过期的时间，不使用含糊的“出错了”。
- 重新生成必须重新读取市场、账户和风险状态。

### 10.3 订单结果未知

- 文案使用“结果未知，正在查询真实订单”，不能显示“失败，请重试”。
- 禁止提供“再次下单”快捷操作。
- 显示最近核对时间、Operation ID、`cloid` 或 `oid`（存在时）。
- 状态解决后保留事件时间线，不覆盖原异常事实。

### 10.4 数据过期和核对

- 图表可显示最后已知数据，但覆盖 `STALE` 标识和更新时间。
- 交易确认入口禁用，并解释“账户或行情尚未核对”。
- 核对中显示具体对象：账户、持仓、活动订单、成交和 K 线。
- 只有服务端返回一致性通过后才能移除限制。

## 11. 安全关键交互规范

### 11.1 环境与交易模式

- `MAINNET` 在顶部状态栏和所有实盘确认卡中持续显示。
- 模拟交易使用 `SIMULATION`；假设讨论使用 `HYPOTHETICAL`。
- 三种模式同时使用文字、图标和颜色区别。
- 模式切换不能改变已生成确认卡和已有 Operation。

### 11.2 增加与降低风险

需要结构化确认：

- 开仓
- 加仓
- 反向开仓
- 增加未成交订单数量
- 提高杠杆
- 放宽或取消止损
- 提高风险上限
- 扩大自动交易授权

不要求交易确认卡：

- `reduce-only` 平仓或减仓
- 收紧止损
- 执行止损止盈
- 撤销未成交的开仓订单
- Kill Switch
- 保护失败后的紧急退出

降低风险动作仍必须来自明确的用户操作或系统安全规则，并显示服务端执行状态。

### 11.3 设备认证

以下操作必须调用操作系统设备认证：

- 提高风险上限
- 启用或扩大自动交易
- 安全暂停后的恢复

应用不得读取、保存或自行校验设备密码。

### 11.4 防误操作

- 安全关键按钮不与普通图表按钮相邻。
- 确认按钮文案包含动作、实盘和品种。
- Kill Switch 与平仓按钮在位置、颜色和文案上严格分离。
- 不提供“全部平仓”按钮。
- 重复点击、窗口切换和客户端重连不得产生第二个 Operation。
- 任何客户端乐观更新都不得伪造订单或保护成功。

### 11.5 告警

- Critical 告警在问题解决或用户明确确认前持续可见。
- 关闭视觉通知不等于解决事件。
- 告警必须说明影响范围：禁止新开仓、已有仓位是否受保护、是否正在紧急退出。
- Email、iOS Push 和软件内投递结果进入审计记录。

## 12. 视觉与颜色语义

### 12.1 视觉方向

视觉基调是“专业交易终端 + 冷静的 AI 助手”：

- 深石墨或深海军蓝背景。
- 中高信息密度。
- 低装饰、低噪声、清晰层级。
- Hermes 使用克制的蓝紫标识。
- 不采用霓虹赌场风、金币、火焰、连胜动画或庆祝动效。

### 12.2 颜色 Token

以下为语义 Token，不规定最终色值：

| Token | 用途 |
| --- | --- |
| `surface.canvas` | 应用主背景 |
| `surface.panel` | 图表、表格和聊天面板 |
| `surface.elevated` | 浮层、确认卡和菜单 |
| `text.primary` | 主要文字 |
| `text.secondary` | 辅助文字 |
| `text.muted` | 元数据和非关键说明 |
| `accent.primary` | 普通主操作 |
| `market.up` | 上涨、正收益 |
| `market.down` | 下跌、负收益 |
| `status.live` | 数据正常 |
| `status.warning` | 过期、临近限制、核对中 |
| `status.critical` | 保护失败、紧急退出、未知结果 |
| `status.info` | 普通系统信息 |
| `agent.hermes` | Hermes 分析与建议 |
| `border.default` | 普通边界 |
| `border.focus` | 键盘焦点 |

规则：

- 采用绿涨红跌。
- 买卖方向不应只靠红绿表达，必须配合“买入/卖出”“多/空”文字和图标。
- `status.critical` 与 `market.down` 必须能通过位置、图标和文案区分。
- 第一版交付深色值；所有组件只能引用语义 Token，禁止把深色背景色硬编码为业务状态。
- 对比度和键盘焦点必须满足无障碍可读要求。

### 12.3 字体与数字

- UI 使用清晰的系统无衬线字体。
- 价格、数量、金额、百分比和时间使用等宽数字。
- 金额显示币种或计价单位。
- 小数精度由服务端元数据决定。
- 正负号不得仅以颜色表达。

### 12.4 动效

- 普通状态变化使用 120–200 ms 的克制过渡。
- Critical 告警不使用持续闪烁。
- 订单处理中可使用低频进度动画，但不能暗示已成交。
- 支持系统“减少动态效果”设置。

## 14. 响应式与 iOS 后续边界

### 14.1 网页和 Tauri

- React/Vite 网页和 Tauri 共享同一桌面 UX 与组件语义。
- Tauri 可调用系统设备认证；网页不得伪造 `device_verified`。
- 若浏览器环境无法满足某项高风险设备认证，界面必须明确要求在受支持客户端完成。
- 桌面窗口缩小时优先保留状态、安全动作和权威数据，不优先保留装饰或次要指标。

### 14.2 窄屏网页

窄屏网页第一版允许：

- 查看账户和持仓
- 查看关键订单和告警
- 使用 Hermes 聊天
- 查看与处理结构化确认卡
- 执行明确的降低风险操作
- 触发 Kill Switch

窄屏网页不要求：

- 完整多面板图表工作区
- 同时展开所有订单、持仓和聊天
- 高级画线与多指标管理

### 14.3 iOS 后续范围

iOS 第一阶段包含：

- 登录和设备登记
- 账户、仓位、订单和风险监控
- Hermes 聊天
- 结构化确认卡
- 实时 Operation 更新
- 持仓保护状态
- 降低风险的仓位管理
- 自动交易状态、暂停和设备认证恢复
- Kill Switch
- iOS Push

iOS 第一阶段不要求：

- 复制完整桌面多面板布局
- 完整专业画线工具
- 多窗口工作区
- 与桌面相同的信息密度
- 在本地计算风险或持有签名密钥

iOS 与桌面必须显示同一个服务端确认、Operation、订单、持仓和保护投影。应用前后台切换不得重复确认或下单。

## 16. 原型验收标准

| ID | 验收标准 |
| --- | --- |
| UX-ACC-001 | 用户在任意交易相关页面都能确认当前是否为 `MAINNET`。 |
| UX-ACC-002 | 用户能在 3 秒内找到数据状态、保护状态、自动交易状态和 Kill Switch。 |
| UX-ACC-003 | Hermes 文本不能在视觉上伪装成“已确认”“已下单”或“已保护”。 |
| UX-ACC-004 | 交易确认卡包含需求规定的全部字段，且字段不可原地修改。 |
| UX-ACC-005 | 最大亏损、交易后总风险、止损和强平价的视觉优先级高于潜在收益。 |
| UX-ACC-006 | 未指定杠杆或有效 Stop Market 时，原型不能进入可确认状态。 |
| UX-ACC-007 | `STALE` 或 `RECONCILING` 时，增加风险入口被禁用且原因明确。 |
| UX-ACC-008 | 确认过期或字段失效后不能复用旧确认，只能重新生成。 |
| UX-ACC-009 | 重复点击确认在 UI 上不会创建第二个执行过程。 |
| UX-ACC-010 | `UNKNOWN_REQUIRES_RECONCILIATION` 不提供重新下单按钮，并显示正在核对真实结果。 |
| UX-ACC-011 | 未核对 Stop Market 前不显示“持仓已保护”。 |
| UX-ACC-012 | `PROTECTION_FAILED`、紧急退出和剩余风险不明使用不可静默的最高级别告警。 |
| UX-ACC-013 | Kill Switch 的文案明确为“停止开仓和增加风险”，不暗示已有仓位会被平仓。 |
| UX-ACC-014 | Kill Switch 后，原型仍允许查看和执行止损、止盈、减仓和平仓。 |
| UX-ACC-015 | 提高风险、启用或扩大自动交易、安全恢复均进入操作系统设备认证流程。 |
| UX-ACC-016 | 普通开仓和加仓确认不要求输入设备密码。 |
| UX-ACC-017 | 自动交易授权明确显示账户、版本、币种、杠杆、资金、风险和允许动作。 |
| UX-ACC-018 | `SAFETY_PAUSED` 条件恢复后不会自动变回 `ENABLED`。 |
| UX-ACC-019 | 普通聊天默认不进入学习集，用户可纠正、撤回或删除学习记录。 |
| UX-ACC-020 | 涨跌遵循绿涨红跌，但方向、风险和状态均不只依赖颜色表达。 |
| UX-ACC-021 | 1280 和 1100 宽度下仍可访问主网状态、告警、确认和 Kill Switch。 |
| UX-ACC-022 | 网页、Tauri 和 iOS 概念稿使用同一服务端状态和字段语义。 |

## 17. 设计评审清单

每个涉及交易的页面在进入开发前必须回答：

1. 当前环境是主网、模拟还是假设讨论？
2. 行情和账户数据是否新鲜并完成核对？
3. 当前信息来自 Hermes、用户还是服务端权威状态？
4. 此操作增加风险还是降低风险？
5. 是否需要结构化确认或设备认证？
6. 重复点击、断线、过期和客户端重启后会怎样？
7. 用户能否看见真实 Operation、订单和保护状态？
8. 异常是否可能被普通通知覆盖或静默关闭？
9. 当前文案是否准确说明 Kill Switch 和安全暂停的作用范围？
10. 页面是否避免让潜在收益压过最大亏损和账户总风险？

只有以上问题均有明确答案，页面才可进入高保真设计或前端实现。
