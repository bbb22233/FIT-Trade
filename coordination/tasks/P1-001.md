## Acceptance checks

- Existing Phase 0 tests plus the new platform verifier pass from `npm test`.
- Platform schemas accept every valid fixture and reject every negative fixture.
- Client-supplied identity, ownership, authorization, server time, token digest,
  and device-verification fields are rejected where the server owns them.
- A reused idempotency key with a different canonical request fails closed.
- Challenge, token, refresh rotation, revocation, device signature, throttle,
  compatibility, retention, and recovery rules are executable and use the
  frozen values.
- MCP/tool inputs still cannot carry user, account, session, confirmation, or
  device-verification authority controlled by a model.
- Inbox/Outbox rules identify the single PostgreSQL transaction that owns each
  business effect, immutable audit event, internal notification, and
  deduplication record.
- Event envelopes bind user and account scope, stable event ID, aggregate ID and
  version, causation, correlation, schema version, and payload digest.
- Every AuditEvent follows the common and scope-specific request-versus-incident
  field matrix in the execution plan. `OWNER` requires user/account;
  `AUTH_SECURITY` and `SYSTEM` follow the exact absence/presence rules. Fixtures
  prove unknown
  identifier, source-only lock, resolved-account lock, WAL incident, and normal
  owner event through intent, persistence, notification, and recovery without a
  phantom owner.
- Enrollment and action Challenge contracts are domain-separated and reject
  fields belonging to the other type. Ordinary and replacement enrollment prove
  the frozen revocation and atomicity differences.
- Enrollment fixtures prohibit user/device/session/account IDs in the wire
  Challenge, bind the opaque subject handle and candidate key, and prove a
  synthetic handle has no accepted state, persistence, or completion path.
- Notification uses the frozen positive field schema, kind and severity enums,
  and tagged scope. It is internal-only and contains no Email, Push, webhook,
  arbitrary text, external address, delivery credential, or arbitrary
  destination.
- Fixtures cover lock expiry/reset, refresh-family hard deadline, health-route
  and unauthenticated-auth-route limits, all WebSocket rate and reauthorization
  boundaries, the three NATS principals, and exact subject allowlists.
- Cross-route password fixtures prove login, ordinary enrollment, and
  replacement enrollment share counters and generic behavior; synthetic
  Challenge completion cannot create a device or session.
- Refresh fixtures prove the seven-day token TTL, earlier family deadline,
  per-family/source rate limits, rotated-token reuse after individual expiry,
  never-rotated individual expiry, family expiry, rotation, and descendant
  revocation behavior.
- Source-key fixtures cover IPv4/IPv6 normalization, key ID, rotation overlap,
  forwarding-header rejection, and raw-IP/log absence.
- The remediation schema rejects a missing discovery commit, component/task,
  severity, evidence, path boundary, owner, base, acceptance, compatibility,
  rollback, or unresolved-risk field.
- Notification fixtures reject every kind/severity mismatch. Audit fixtures
  distinguish request-triggered and background `AUTH_SECURITY` from `SYSTEM`
  incident linkage and always reject trading-account ID outside `OWNER`.
- Recovery evidence cannot present target RPO/RTO as measured results.
- Diff and object checks prove all non-manifest Phase 0 contract files are
  byte-identical to the base.
